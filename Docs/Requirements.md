# AutoLogMiner 需求文档（Requirements）

> 文档版本：1.0 · 更新日期：2026-09-10 · 对应代码：`app/`（T1–T19 已完成）
> 本文档描述 AutoLogMiner 作为「AI 驱动运维工作台」的功能与非功能需求，是架构、实施计划与风险文档的上游输入。

## 1. 背景与目标

### 1.1 背景

传统服务器排障依赖工程师手工 SSH 登录、逐条敲命令、凭经验阅读日志。日志量大、
信息密度低，人工筛选耗时且容易漏掉关键信号；多台服务器之间缺乏统一视图，
故障发现、定位、修复、归档分散在多个工具里，无法形成闭环。

AutoLogMiner 把「监控 → 健康检查 → 告警 → 日志诊断 → 远程执行 → 事件归档」
收敛到一个本地优先的 Web 工作台里，用 LLM 承担日志压缩与根因推理，用结构化的
命令安全策略承担「AI 建议不要直接变成灾难」的兜底责任。

### 1.2 产品目标

1. 让工程师在一个页面上看清所有服务器的实时状态与历史趋势。
2. 用 LLM 把噪声日志压缩成「摘要 + 分级 + 根因 + 可执行修复步骤 + 预防建议」。
3. 让诊断结果可以直接转化为受控的远程操作，并全程留痕可审计。
4. 在没有真实服务器时也能完整体验产品（演示模式）。
5. 默认安全：单管理员鉴权、最小攻击面、命令白名单、路径防护。

### 1.3 非目标（本期不做）

- 不构建多用户账号体系、RBAC、团队协作。
- 不建设集中式日志平台（ELK/Loki），仍按需拉取日志。
- 不做告警规则引擎（自定义表达式、复杂抑制），只做阈值 + 冷却。
- 不替换 SQLite，不引入 ORM，不引入 Redis/Celery 等新基础设施。
- 不重写前端框架，保持 vanilla JS 零构建。

## 2. 用户与场景

### 2.1 目标用户

| 角色 | 诉求 |
|------|------|
| 运维工程师 | 快速发现异常、定位根因、受控修复 |
| 后端开发者 | 排查生产/预发环境故障，理解日志含义 |
| 学生 / 自学者 | 通过演示模式理解运维排障流程 |

### 2.2 核心场景

- **场景 A（巡检）**：用户打开仪表盘，看到 3 台服务器，其中 1 台 CPU 89% 标红，
  点进详情页查看 24h 趋势，确认是持续高负载而非瞬时抖动。
- **场景 B（诊断）**：用户把 nginx error.log 粘贴到诊断页，SSE 流式返回结构化诊断，
  P1 严重，根因是 upstream 连接超时，修复步骤含 `systemctl restart nginx`。
- **场景 C（受控修复）**：用户在服务器详情页一键执行修复命令，系统按白名单判定为
  「直接执行档」或要求二次确认，执行结果写入审计日志。
- **场景 D（演示）**：没有服务器的新用户点击「演示数据」，立即获得 3 台虚拟服务器、
  24h 健康曲线和若干告警，完整体验所有页面。

## 3. 功能需求（FR）

### FR-1 服务器管理

- FR-1.1 支持服务器的增、删、改、查，字段含名称、主机、端口、用户名、认证方式。
- FR-1.2 认证方式支持密码与密钥文件两种；密码使用 Fernet 对称加密后落库。
- FR-1.3 支持 production / staging / development 环境标签。
- FR-1.4 支持连通性探活，结果回写 `online` / `offline` 状态。
- FR-1.5 支持按服务器配置定时检查间隔、CPU/内存/磁盘阈值与告警 Webhook URL。
- FR-1.6 支持一键导出全部服务器配置为纯文本附件。
- FR-1.7 列表与详情响应不得回传加密后的 SSH 密码或密钥路径。

### FR-2 健康检查

- FR-2.1 一次 SSH 调用采集 7 类指标：CPU、内存、磁盘、负载、Top 进程、
  关键服务状态（nginx/docker/mysql 等）、最近系统错误。
- FR-2.2 服务端把原始输出解析为结构化指标（百分比、负载、服务状态字典）。
- FR-2.3 调用 LLM 生成不超过三句的健康评估摘要。
- FR-2.4 LLM 不可用时自动降级为空摘要，指标仍正常入库。
- FR-2.5 指标全部处于正常区间时跳过 LLM 调用以节省成本。
- FR-2.6 提供最近 N 次检查记录与按小时聚合的趋势时序数据。

### FR-3 告警

- FR-3.1 对 CPU/内存/磁盘三项指标做阈值比对，超标即生成告警。
- FR-3.2 超标 20% 以上判为 critical，否则 warning。
- FR-3.3 同一服务器同类指标在冷却期内（默认 30 分钟）不重复告警。
- FR-3.4 Webhook URL 含 `feishu` 时发送飞书交互卡片，否则发送钉钉 Markdown。
- FR-3.5 提供告警列表、统计与「标记恢复」能力。

### FR-4 日志诊断

- FR-4.1 支持两种输入：服务器详情页远程拉取（文件路径或 journalctl）。
- FR-4.2 文件路径支持 Shell glob（如 `/var/log/nginx/error.log*`），合并轮转文件。
- FR-4.3 诊断页支持粘贴或上传日志。
- FR-4.4 提供 SSE 流式输出，前端实时渲染 LLM 增量文本。
- FR-4.5 输出结构化结果：问题摘要、P0–P3 分级、根因、修复步骤、预防建议。
- FR-4.6 诊断完成后写入历史；流式解析失败时静默跳过保存但不断流。
- FR-4.7 支持把单条诊断导出为 Markdown 报告。
- FR-4.8 智能日志过滤：信号行匹配 + 上下文 + 去重 + 截断 + 安全尾行。

### FR-5 远程命令执行

- FR-5.1 支持在服务器上执行命令并返回 stdout / stderr / exit_code。
- FR-5.2 原始命令包含 shell 元字符时直接拒绝（HTTP 400）。
- FR-5.3 首 token 命中白名单进入「直接执行档」；否则进入「确认档」，
  必须显式提交 `confirm=true` 才执行。
- FR-5.4 所有分支（含被拦截）都写入 `execution_logs` 审计表。
- FR-5.5 参数 token 必须匹配白名单字符集，禁止空格、引号与特殊字符。

### FR-6 事件时间线

- FR-6.1 聚合诊断、健康检查、告警、命令执行四类事件。
- FR-6.2 按时间倒序返回，含类型、时间戳、摘要、服务器名、严重程度。

### FR-7 知识库

- FR-7.1 列出、上传、删除 `.md` 知识文件。
- FR-7.2 知识库内容在诊断时自动注入系统提示词。
- FR-7.3 上传与删除必须阻止路径穿越，仅接受纯 basename 且以 `.md` 结尾。

### FR-8 LLM 供应商

- FR-8.1 支持供应商增删改查与「设为默认」（全局互斥）。
- FR-8.2 任一供应商的 `api_key` 响应时脱敏为「前 4 位 + **** + 后 4 位」。
- FR-8.3 至少保留一个供应商，禁止删光。
- FR-8.4 默认供应商缺失或 `api_key` 为空时，回退到 `.env` 的 LLM 三元组。

### FR-9 演示模式

- FR-9.1 一键生成 3 台虚拟服务器、24h 模拟健康数据与若干告警。
- FR-9.2 一键重置只清除演示数据（`is_demo=1`），真实服务器及其关联数据保留。

### FR-10 仪表盘与对比

- FR-10.1 聚合在线/离线/未知计数与每台服务器的最新指标和 AI 摘要。
- FR-10.2 支持选择多台服务器做指标横向对比。

### FR-11 诊断历史

- FR-11.1 分页列出诊断记录，按时间倒序。
- FR-11.2 按 ID 查询单条诊断详情。
- FR-11.3 导出单条诊断为 Markdown。

## 4. 非功能需求（NFR）

### NFR-1 安全

- NFR-1.1 单管理员令牌鉴权：`ADMIN_TOKEN` 非空时，除豁免外所有 `/api/*` 请求
  必须携带 `Authorization: Bearer <token>`，缺失或错误返回 401。
- NFR-1.2 豁免清单固定为：`GET /api/health`、`/static/*`、9 条页面路由。
- NFR-1.3 令牌比较使用常量时间算法（`secrets.compare_digest`）。
- NFR-1.4 默认仅绑定 `127.0.0.1`，避免未鉴权时暴露到公网。
- NFR-1.5 禁用自动生成的 API 文档（`/docs`、`/redoc`、`/openapi.json` 均 404）。
- NFR-1.6 修复远程命令注入、路径穿越、存储型 XSS、外键失效、demo 越权删除。
- NFR-1.7 开启 `PRAGMA foreign_keys=ON`，保证 `ON DELETE CASCADE` 生效。
- NFR-1.8 模块导入无副作用：不在 `import` 阶段写 `.env` 或生成密钥。

### NFR-2 可靠性

- NFR-2.1 SSH 连接失败自动重试 3 次，指数退避 1s/2s/4s。
- NFR-2.2 SQLite 使用 WAL 模式与 `busy_timeout=3000`，支持并发读写。
- NFR-2.3 SSE 无论成功或异常都必须以 `data: [DONE]` 收尾。
- NFR-2.4 旧库 `logdoctor.db` 迁移必须 WAL 安全、幂等、可回滚。
- NFR-2.5 调度任务 `max_instances=1`，防止任务重叠。

### NFR-3 性能

- NFR-3.1 智能日志过滤将超长日志压缩到原始体量的 5–15%。
- NFR-3.2 指标正常时跳过 LLM，节省 80% 以上的 API 调用。
- NFR-3.3 每日清理 30 天前的健康检查与执行日志。

### NFR-4 可维护性

- NFR-4.1 全仓库命名统一为 `AutoLogMiner`（仅保留旧名迁移兼容代码）。
- NFR-4.2 提供 pytest 回归套件，全部 mock，无网络、无 secret 依赖。
- NFR-4.3 提供 ruff 静态检查配置与 GitHub Actions CI。
- NFR-4.4 提供 Docs 四件套（本文档、架构、实施计划、风险）。

### NFR-5 兼容性

- NFR-5.1 支持 Python 3.10+（目标版本 `py310`）。
- NFR-5.2 前端为零构建 vanilla JS，Chart.js 与 GSAP 通过 CDN 引入。
- NFR-5.3 CDN 加载失败时降级提示，不白屏、按钮仍可点。

## 5. 验收标准

1. 无 token 访问 `/api/servers` 返回 401；带正确 token 返回 200。
2. `POST /api/servers/{id}/execute` 收到 `ls; rm -rf ~` 时返回 400，且远端未被破坏。
3. 删除服务器后，其关联的健康检查/告警/执行日志无孤儿残留。
4. 上传文件名 `../evil.md` 被拒绝，仓库外无落盘文件。
5. demo reset 后真实服务器与其数据原样保留。
6. LLM 默认供应商 key 为空时，诊断走 `.env` 回退。
7. SSE 正常与异常路径均以 `[DONE]` 结束。
8. `ruff check .` 通过，`pytest -q` 全绿且全程无真实网络。
9. README 与 Docs 描述与实际代码行为一致。

## 6. 约束与假设

- 运行环境为单机（Windows 10 + WSL Ubuntu），服务默认 `127.0.0.1:8080`。
- 数据库文件固定为 `data/autologminer.db`。
- 管理员令牌长度建议 32 位十六进制（`openssl rand -hex 16` 生成）。
- SSH 使用 `known_hosts=None`，适用于内网可信环境，不防中间人。
- LLM 供应商密钥在数据库中以明文存储，仅在响应时脱敏，依赖 DB 文件自身权限保护。
